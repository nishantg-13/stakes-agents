STAKES: spend agent compute where mistakes can't be undone

Stakes-weighted test-time deliberation for tool-using LLM agents. Extra reasoning goes to actions whose errors are costly and irreversible, not merely to actions the model is unsure about.

Prototype running on τ²-benchPreliminary resultsWorkshop paper target: Feb 2027

Project summary

  1. Problem. LLM agents increasingly take irreversible actions through tools (cancellations, refunds, order changes). Existing methods spend extra compute only where the model is uncertain and ignore how costly a mistake would be.
  2. Method (STAKES). A model-agnostic agent harness that types every tool call by reversibility (read, reversible, compensable, irreversible), estimates error risk from disagreement among sampled actions, and spends extra deliberation (re-voting, verification, asking the user) in proportion to expected error cost.
  3. Evaluation. A compute-matched reliability comparison on τ²-bench customer-service tasks with Gemini models. STAKES is compared against uniform and uncertainty-only compute allocation on success, consistency (pass^k), irreversible-error rate and cost. Success is graded from database state, not by LLM judges.
  4. Prototype. A working pipeline: an effect-type registry for every tool, an effect ledger that flags wrong writes against reference trajectories, reliability metrics with bootstrap confidence intervals, and four agent modes run side by side on the same tasks.

The idea

Most of an agent's steps are reads: looking up a reservation, checking a flight. A wrong read costs a few tokens, because the agent can just read again. A few steps commit state that cannot be restored, such as cancelling a non-refundable booking or issuing a travel certificate. Uncertainty-based methods treat these steps alike and spend on whatever the model is unsure about. They spend nothing on a confident action that happens to be wrong and irreversible.

STAKES allocates deliberation by the expected loss it can prevent, following the classical value-of-computation rule from metareasoning:

value(deliberate at step t) = P(action wrong) × cost(action wrong | reversibility) × P(deliberation fixes it) − price × tokens

Each tool is labelled once with its effect type, using the agent's own tools and the domain policy to decide whether an action can be undone:

Readno state changeget_reservation_details
Reversibleundo with own toolsupdate_reservation_passengers
Compensableundo only at a costupdate_reservation_flights
Irreversibleno undo existscancel_reservation

Baseline
Single run. Disagreement is measured silently at writes but never acted on.
Uncertainty-only
Samples and votes at every tool step; verifies only when samples disagree.
Verify every write
Simple rule: a policy check before any state change, no sampling.
STAKES v0
Nothing on reads. Votes on writes. Verifies every compensable or irreversible write, even when confident.

A failure STAKES is built for

From the first smoke run (airline task 1, Gemini 2.5 Flash, baseline agent). The customer claims a support representative already approved a cancellation that the airline policy does not allow; the correct behaviour is to refuse. The agent found the right booking and then cancelled it. All three silent re-samples made the same call, so an uncertainty-based method would have seen no reason to look twice.

turn 2–7 get_user_details, get_reservation_details ×5 [READ]
turn 11 cancel_reservation("Q69X3R") [IRREVERSIBLE]
re-samples: Q69X3R, Q69X3R, Q69X3R → disagreement p̂ = 0.0
reference solution: no cancellation · ledger: wrong write · episode failed

This is one anecdote, not evidence. Whether confident wrong writes are a large share of failures is exactly what the pre-registered pilot measures (GO if they make up at least 30% of failures).

How to read this

  • Direction, not evidence. STAKES has the highest consistency (pass^2 0.60 vs 0.40 for the baseline), but with 15 tasks every interval overlaps. No difference here is statistically significant.
  • Uncertainty-only spent the most and gained the least in consistency. At 2.5× the baseline's tokens its pass^2 did not move, which matches the motivating hypothesis: much of its budget goes to reads (78% of the agent's tool calls are reads).
  • The simple "verify every write" rule is a strong competitor. It matches STAKES on single-run success at lower cost. Separating the two is the central question for the full study, using a cost-matched budget sweep.
  • The core premise holds so far. In the baseline runs, 33% of failures came from a confident wrong write (all re-samples agreed), just above the pre-registered 30% bar for continuing. That is 5 of 15 failures, so it is a first signal only.
  • Every form of deliberation halved wrong irreversible writes (0.27 to 0.13 per episode). The verifier is mostly accurate: of 34 high-stakes actions it sent back for revision across the three methods, 27 were genuinely wrong and 7 were correct actions it blocked by mistake.
  • Measurement check. An early version of the wrong-write detector flagged 14% of writes in successful episodes, because the agent adds harmless extra fields to its calls. After the fix the rate is 0%, and all numbers above use the corrected detector.

What is built

  • Effect registry for every airline and retail tool, each label with a written rationale; a test fails if any state-changing tool is unlabelled.
  • Effect ledger that records every tool call and flags writes that match no step of the reference solution.
  • Reliability metrics: pass^k and pass@k with unbiased estimators, bootstrap confidence intervals over tasks, irreversible-error rate.
  • Agent harness with four modes on one code path, so the comparison differs only in where compute is spent.
  • Pilot runner: resumable, records cost and tokens per call, and applies a go/no-go rule fixed before any data was seen.
  • 32 automated tests, including full offline τ²-bench episodes with a scripted model.
